# Authorization Endpoint

**Status: target design.** See [README](./README.md).

`GET /oauth2/authorize` — the only endpoint in this design reached by a browser rather than by a
service. It takes attacker-influenceable input in a URL, so every rule here exists to keep a
malformed or hostile request from producing a redirect.

`POST` is not supported. OIDC Core §3.1.2.1 permits it; this phase omits it because a form POST to
the authorization endpoint adds a second parsing path and a CSRF surface for no gain with a
server-side BFF that can always build a URL.

## Request parameters

| Parameter | Required | Encoding and bounds | Rule |
| --- | --- | --- | --- |
| `response_type` | Yes | ASCII | MUST be exactly `code` |
| `client_id` | Yes | 1–100 chars, matches `MaxAppIdLength` | Resolved with the existing normalized-AppId lookup |
| `redirect_uri` | Yes | 1–500 chars | Exact ordinal comparison against the registered set; see [ClientModel](./ClientModel.md#request-time-comparison) |
| `scope` | Yes | Space-delimited, 1–200 chars total | MUST contain `openid`; every value MUST be in the application's allow list |
| `state` | Yes | 22–128 chars, `[A-Za-z0-9._~-]` | Opaque to SignaCore; echoed byte-for-byte in every response that redirects |
| `nonce` | Yes | 22–128 chars, `[A-Za-z0-9._~-]` | Opaque to SignaCore; copied verbatim into the ID token |
| `code_challenge` | Yes | Exactly 43 chars, `[A-Za-z0-9._~-]` | Base64url of a SHA-256 digest, unpadded |
| `code_challenge_method` | Yes | ASCII | MUST be exactly `S256` |
| `prompt` | No — rejected | — | Any value MUST fail with `invalid_request` |
| `max_age` | No — rejected | — | Any value MUST fail with `invalid_request` |
| `acr_values` | No — rejected | — | Any value MUST fail with `invalid_request` |
| `response_mode` | No — rejected | — | The response mode is always `query`; sending the parameter MUST fail with `invalid_request` |
| `request`, `request_uri`, `registration` | No — rejected | — | MUST fail with `request_not_supported`, `request_uri_not_supported`, `registration_not_supported` respectively |
| Anything else | Ignored | — | Unknown parameters are neither read nor echoed |

`state` and `nonce` are required rather than recommended. A BFF that omits `state` has no CSRF
defence on its own callback, and one that omits `nonce` cannot detect a replayed ID token. Both are
generated by the client from a CSPRNG; SignaCore enforces the length and alphabet but makes no claim
about their entropy, which is the client's responsibility. The 22-character floor is what 128 bits
of base64url costs, so a compliant generator passes and a counter or a timestamp does not.

`prompt`, `max_age`, and `acr_values` are rejected rather than ignored. Silently ignoring `max_age`
would let a client believe it had forced a fresh authentication when it had not — a security
statement the server cannot honour in this phase. Rejecting is the honest answer, and it is also
what makes adding the capability later a non-breaking change: no client can already be sending a
value that used to be ignored.

### Duplicate parameters

A parameter appearing more than once in the query string MUST fail with `invalid_request`, even when
the values are identical, and MUST fail before the value is read. Taking "the first" or "the last"
means the outcome depends on which parser reads the URL — SignaCore's, a proxy's, or the client's —
and parameter-pollution attacks live in exactly that disagreement.

## Validation order

The order is normative, not incidental: it is what decides whether a failure can be redirected.

1. `client_id` present, well-formed, resolves to an application, application is active, and
   `allow_authorization_code` is `true`.
2. `redirect_uri` present and exactly matches one registered for that application.

   **After step 2 and only after step 2, redirection is permitted.**
3. `response_type` is `code`.
4. `prompt` / `max_age` / `acr_values` / `response_mode` / `request` / `request_uri` /
   `registration` absent.
5. No duplicate parameters.
6. `state` present, within bounds and alphabet.
7. `scope` present, contains `openid`, and every value is in the application's allow list.
8. `nonce` present, within bounds and alphabet.
9. `code_challenge_method` is `S256`; `code_challenge` present and exactly 43 characters of the
   base64url alphabet.
10. Identity session: present, unexpired, and within `identity_session_max_age`. If not, the browser
    goes to login; see [IdentitySession](./IdentitySession.md).
11. The authenticated account is enabled.

Steps 1 and 2 come first because they are the only two that decide *where* a response may go. Every
later step is a decision about *what* the response says.

## Error routing

| Failing step | Where the error goes | Form |
| --- | --- | --- |
| 1 — unknown, inactive, or non-interactive client | SignaCore error page, HTTP 400 | Rendered page, no redirect, no `Location` header |
| 2 — missing or unmatched `redirect_uri` | SignaCore error page, HTTP 400 | Same |
| 3–9 — protocol errors | 302 to the verified `redirect_uri` | `error`, `error_description`, `state`, `iss` in the query |
| 11 — account disabled after login | 302 to the verified `redirect_uri` | `error=access_denied` |
| User cancels at the login page | 302 to the verified `redirect_uri` | `error=access_denied`, `error_description=The user cancelled the request.` |
| Internal failure after step 2 | 302 to the verified `redirect_uri` | `error=server_error` |
| Internal failure before step 2 | SignaCore error page, HTTP 500 | Rendered page |

The local error page MUST NOT contain the submitted `redirect_uri` as a hyperlink, MUST NOT set a
`Location` header, and MUST NOT reflect any submitted value into HTML without contextual encoding.
It says which parameter was wrong and that the application's registration should be checked; it does
not say whether the `client_id` exists, because that turns the page into an enumeration oracle.

Redirected errors use the exact code names below, and each carries `state` and `iss`.

| Code | Emitted when | Source |
| --- | --- | --- |
| `invalid_request` | Missing, duplicated, malformed, or rejected parameter | RFC 6749 §4.1.2.1 |
| `unsupported_response_type` | `response_type` is not `code` | RFC 6749 §4.1.2.1 |
| `invalid_scope` | `openid` absent, or a scope is outside the allow list | RFC 6749 §4.1.2.1 |
| `access_denied` | The user cancelled, or the account is disabled | RFC 6749 §4.1.2.1 |
| `server_error` | Unexpected failure after the client is verified | RFC 6749 §4.1.2.1 |
| `temporarily_unavailable` | The server is deliberately shedding load | RFC 6749 §4.1.2.1 |
| `request_not_supported` | `request` was supplied | OIDC Core §3.1.2.6 |
| `request_uri_not_supported` | `request_uri` was supplied | OIDC Core §3.1.2.6 |
| `registration_not_supported` | `registration` was supplied | OIDC Core §3.1.2.6 |

`error_description` is a fixed English sentence chosen from a closed set. It MUST NOT contain a
username, an account identifier, a session identifier, a cookie value, an internal exception message,
or a stack trace, and MUST NOT distinguish "no such account" from "wrong password".

## Success response

```
HTTP/1.1 302 Found
Location: https://console.example.com/signin-oidc?code=<43-char-base64url>&state=<echoed>&iss=https%3A%2F%2Fsignacore.example.com
Cache-Control: no-store
Pragma: no-cache
```

- Parameters go in the query string. `response_mode` is always `query`; `fragment` and `form_post`
  are not implemented, which is why the parameter is rejected rather than defaulted.
- `iss` is the issuer, identical to the `iss` claim in issued tokens and to `issuer` in discovery
  (RFC 9207). It is present on success **and** on every redirected error, so a client talking to two
  issuers cannot be induced to redeem a code at the wrong one.
- `state` is echoed byte-for-byte from the request. No trimming, no re-encoding, no normalization.
- The response body is empty. Any `Location` value is also `no-store`, because an authorization code
  in a cached URL is a code in someone else's history.

## Anti-caching and referrer

Every response from this endpoint, success or failure:

```
Cache-Control: no-store
Pragma: no-cache
Referrer-Policy: no-referrer
```

`Referrer-Policy: no-referrer` matters on the redirect target: without it, a page at the redirect
URI that loads a third-party asset leaks the full callback URL — code included — in the `Referer`
header. The code is single-use and expires in 60 seconds, but 60 seconds is enough.

## Concurrency

Two authorization requests for the same account, application, and redirect URI may run at once and
both succeed; they produce two independent codes. Codes are not deduplicated, not reused, and not
invalidated by one another. Single-use is enforced at redemption
([TokenEndpoint](./TokenEndpoint.md#single-use-consumption)), not by refusing to issue.

## Rate limiting

| Partition | Limit | Rationale |
| --- | --- | --- |
| `authorize:{client_id}` | 60 / minute | Bounds code-generation load from one misbehaving client |
| `authorize:{client_ip}` | 30 / minute | Bounds scanning from one source |

Rejection is HTTP 429 with the existing problem-details body, rendered locally and never redirected:
a 429 delivered as `error=temporarily_unavailable` to a redirect URI would let an attacker use the
limiter to force a chosen error at the client.
