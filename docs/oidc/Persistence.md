# Persistence

**Status: target design.** See [README](./README.md).

Every change here is additive. No existing table is dropped, no existing column is renamed or
retyped, no existing default changes. A deployment that never registers an interactive client
carries empty tables and behaves exactly as it did before.

Both histories move together: PostgreSQL in `src/SignaCore.Database`, SQLite in
`src/SignaCore.Database.Migrations.Sqlite`. A pull request that adds a migration to one and not the
other is incomplete, and the SQLite migration is generated by `dotnet ef` against its own factory —
never hand-copied from the PostgreSQL one. See [migrations](../database/migrations.md).

## New tables

### `authorization_codes`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `code_digest` | string(71) | `sha256:` + 64 lowercase hex, the `RefreshTokenDigest` construction. Unique index. The plaintext is never stored |
| `client_id` | string(100) | The application the code was issued to |
| `account_id` | UUID | References `accounts` |
| `identity_session_id` | UUID | References `identity_sessions` |
| `redirect_uri` | string(500) | The exact value from the authorization request |
| `scope` | string(200) | Granted scope, space-delimited, normalized order |
| `nonce` | string(128) | Plaintext — it must be copied verbatim into the ID token |
| `code_challenge` | string(43) | Base64url SHA-256, as supplied |
| `auth_time` | timestamptz | When the identity session was established |
| `created_at` | timestamptz | |
| `expires_at` | timestamptz | `created_at` + 60 seconds |
| `consumed_at` | timestamptz, null | Null until redeemed; the conditional-update target |

`code_challenge_method` is not a column. It is always `S256`, and a column would invite a second
value.

Indexes: unique on `code_digest`; `(expires_at)` for cleanup; `(account_id, created_at)` for audit
lookups.

`nonce` in plaintext is a deliberate departure from the gap document's sketch. A digest cannot be
echoed into the ID token, which is the whole purpose of the value, and the nonce is not a
credential: it is already in the browser's URL bar and it authorizes nothing on its own.

### `identity_sessions`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Primary key; the value the cookie carries |
| `account_id` | UUID | References `accounts` |
| `created_at` | timestamptz | Also the `auth_time` for tokens from this session |
| `last_seen_at` | timestamptz | Advanced on use; written at most once per minute |
| `idle_expires_at` | timestamptz | `last_seen_at` + idle window |
| `absolute_expires_at` | timestamptz | `created_at` + absolute lifetime, never extended |
| `revoked_at` | timestamptz, null | |
| `revocation_reason` | string(32), null | `logout`, `account_disabled`, `code_replay`, `administrative` |
| `auth_method` | string(32) | `Password` in this phase |
| `client_ip` | string(45), null | Existing accessor; IPv6-sized |
| `user_agent` | string(256), null | Truncated |

Indexes: primary key; `(account_id)` for revoke-all-for-account; `(absolute_expires_at)` for cleanup.

The cookie carries `id` and nothing else. Every claim is read from this row, which is what makes
revocation work on an instance that never saw the login.

### Interactive client configuration

The fields in [ClientModel](./ClientModel.md#interactive-client-configuration) are stored as follows.

Scalars are added as nullable columns on `app_registrations`: `allow_authorization_code`,
`client_type`, `allow_refresh_token`, `allowed_scopes`, `identity_session_max_age`. They join a row
that already carries per-feature settings for LDAP, SMS, WeChat, and audience mode, so the shape is
established and the alternative — a one-to-one companion table — would add a join to a hot lookup for
no gain.

The URI sets get their own table, because they are multi-valued:

`app_redirect_uris`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `app_id` | string(100) | Logically references `app_registrations.app_id` |
| `uri` | string(500) | Stored normalized, per [ClientModel](./ClientModel.md#registration-time-normalization) |
| `kind` | string(16) | `redirect` or `post_logout` |
| `created_at` | timestamptz | |

Unique index on `(app_id, kind, uri)`. At most 10 rows per `(app_id, kind)`, enforced in the domain —
a database constraint for a count is provider-specific and awkward in both histories.

## PostgreSQL and SQLite

| Property | PostgreSQL | SQLite |
| --- | --- | --- |
| Instances | Many | Exactly one |
| Atomic code consumption | `UPDATE … WHERE consumed_at IS NULL … RETURNING` | The same statement, plus a single writer |
| Timestamps | `timestamp with time zone` | Existing SQLite conversion, UTC throughout |
| Session revocation across instances | Shared rows | Not applicable |
| Rate limiting | Per instance | Single instance, so per instance is global |

SQLite deployments get the full flow and remain single-instance, which is not a new restriction.
Authorization codes make the reason sharper: a second SQLite writer would break atomic redemption
rather than merely slow it down, so "one instance" moves from a performance note to a correctness
requirement.

Both providers must be covered by the concurrency test for double redemption. The PostgreSQL variant
runs it across two instances against one database; the SQLite variant runs it as concurrent requests
against one instance.

## Compatibility and rollback

- Every migration is additive. Down-migrations drop only what the corresponding up-migration created.
- Rolling back after interactive clients exist destroys their configuration and sessions, and any
  BFF depending on the flow stops working. It does not affect existing grants, existing tokens,
  callbacks, or `/api/auth/*`.
- The new columns on `app_registrations` are nullable with defaults matching current behaviour, so an
  old binary reading a new database sees rows it understands.
- Applying the migrations to a database with no interactive clients is a no-op in effect: empty
  tables and five unused columns.
- The migration series is split across the implementation tasks; each pull request adds its own
  migration to both histories, and none rewrites an earlier one.

## Cleanup

The existing 24-hour job (`CleanupIntervalHours`) removes:

- `authorization_codes` where `expires_at` is more than 24 hours past, consumed or not.
- `authorization_requests` past `expires_at`.
- `identity_sessions` past `absolute_expires_at`, and revoked sessions older than 24 hours.

Consumed codes survive 24 hours on purpose. Deleting one at consumption makes a replay
indistinguishable from a code that never existed, and only one of those should revoke a refresh
token and raise an alert.

Each implementation task that creates a table adds its page under `docs/database/tables/`, following
the existing format, and appends to the history sentence in
